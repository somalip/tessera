# Tessera: Sub-1GB Per-Language Coding LLMs + VS Code Router

Hand this file to Codex as the repo's source of truth (copy section 9 into `AGENTS.md`).

---

## 1. Goals and hard constraints

| Constraint | Target |
|---|---|
| Shipped model artifact size | **< 1.0 GB on disk each** (quantized, incl. tokenizer + metadata) |
| Specialization | One model per language (Python, TypeScript, Rust, Go, Java, C/C++, ...) |
| Primary tasks | Inline completion (FIM), short chat/explain, edit/refactor, test generation |
| Runtime | Local, CPU-first (llama.cpp), optional GPU/Metal; no cloud needed |
| Router | VS Code extension that picks, loads, and unloads the right model |
| Licensing | Only permissively licensed training data and base weights |

**Size math (why the budget works):** file size ≈ params × bits/8.
- 1.5B params @ Q4_K_M (~4.8 bits) ≈ 0.9 GB (upper limit, tight)
- 1.0B params @ Q4_K_M ≈ 0.6 GB (comfortable)
- 0.5B params @ Q8 ≈ 0.55 GB
Design target: **0.5B–1.3B params at 4-bit.** Keep a 10% size margin under 1 GB.

## 2. System overview

```
                 ┌──────────────────────── TRAINING PLANE (offline) ────────────────────────┐
 Raw code  ──►  Data pipeline ──► Per-language corpus ──► Train recipe ──► Eval gate ──► Quantize ──► Model package
 (permissive)   (filter/dedupe)   (+ synthetic data)      (CPT→SFT→RL)    (pass/fail)   (QAT/GGUF)   (.tcm + manifest)
                 └──────────────────────────────────────────────────────────────────────────┘
                                                      │ registry.json (signed, versioned)
                 ┌──────────────────────── RUNTIME PLANE (user machine) ────────────────────┐
 VS Code ext ──► Router ──► Model Host (llama.cpp server, 1 process per loaded model) ──► completions/chat
   (TS)          │  language detect · project sniff · LRU load/unload · fallback · telemetry(local)
                 └──────────────────────────────────────────────────────────────────────────┘
```

Two independent planes with a stable contract between them: the **model package format** + **registry manifest**. Codex can build each plane in parallel against that contract.

## 3. Model strategy

### 3.1 Start from a base, don't pretrain from scratch
Pretraining from scratch at this scale needs trillions of tokens to be competitive. Instead:

1. **Pick one small, permissively licensed, code-capable base** (0.5B–1.5B). Shortlist and verify licenses/current availability before committing (this landscape moves fast): Qwen2.5-Coder 0.5B/1.5B (Qwen3-family small variants if available), SmolLM2/SmolLM3 1.7B-class, StarCoder2-3B is too large unless pruned.
2. **Use the same base architecture for every language.** One tokenizer, one runtime path, one set of kernels. Per-language differences live in weights only.
3. **Optional: prune the vocabulary.** A single-language model doesn't need a 150k vocab. Trimming embeddings to a language-relevant vocab (code + English + that language's idioms) can save 100-200 MB at 4-bit. Add as an experiment (M6), not baseline.

### 3.2 Training recipe (per language, same pipeline)
| Stage | What | Notes |
|---|---|---|
| A. Continued pretraining | 5–30B tokens of that language's code + docs + Q&A, FIM-formatted (PSM/SPM, ~50% FIM rate) | Mix ~10–15% general English/NL replay to avoid forgetting |
| B. Distilled SFT | Instruction/edit/test-writing data generated by a larger teacher, **filtered by execution** | Check teacher ToS permits training on outputs |
| C. Execution-verified RL (or rejection sampling) | Reward = tests pass, compiles, linter clean | Start with rejection-sampling fine-tuning (simpler); add GRPO-style RL later |
| D. Quantization-aware finish | QAT or post-training quant with calibration on in-language code | Target Q4_K_M; compare to IQ4/Q5 vs size budget |
| E. Eval gate | Must beat the base and meet thresholds or the build fails | See section 6 |

### 3.3 Data pipeline
- **Sources:** The Stack v2 (filter to permissive licenses, language subset), language official docs (license-checked), permissively licensed package docs, Stack Overflow-style Q&A (license-aware), synthetic data.
- **Filters:** license allowlist, exact + near-dup (MinHash), quality heuristics (parse success via tree-sitter, line-length, autogen detection), PII/secret scrubbing, **benchmark decontamination** against all eval sets.
- **Per-language "verifier" harness:** sandboxed compile/test runner (Docker/nsjail). This is the highest-leverage component: it powers data filtering, RL reward, and evals.
- **Synthetic generation:** teacher writes (problem, solution, tests) → run in sandbox → keep only passing triples.

### 3.4 Compute plan
- Single-node 8×H100-class or equivalent rented GPUs per language is plenty for 1B-scale CPT. Estimate ~1B params × 10B tokens ≈ 6e19 FLOPs (a few GPU-days). Budget for 5–10 ablation runs per language.
- Framework: PyTorch + Hugging Face Transformers/TRL, `torchtune` or `axolotl` for configs, DeepSpeed/FSDP. Config-driven (YAML), one config per language inheriting from `base.yaml`.

## 4. Model package format (the contract)

A model ships as a directory (zipped as `.tcm`):

```
python-tiny-v0.3.0/
  model.Q4_K_M.gguf        # weights, < 1.0 GB total package
  manifest.json            # see below
  eval_report.json         # frozen eval results
  LICENSE / NOTICE
```

`manifest.json`
```json
{
  "id": "python-tiny",
  "version": "0.3.0",
  "language_ids": ["python"],
  "vscode_language_ids": ["python"],
  "file_globs": ["**/*.py", "**/*.pyi"],
  "base_model": "qwen2.5-coder-1.5b",
  "params": 1.1e9,
  "quant": "Q4_K_M",
  "size_bytes": 712345678,
  "context_length": 8192,
  "prompt_formats": {
    "fim": {"prefix": "<|fim_prefix|>", "suffix": "<|fim_suffix|>", "middle": "<|fim_middle|>"},
    "chat_template": "chatml"
  },
  "capabilities": ["fim", "chat", "edit"],
  "min_runtime": {"llama_cpp_build": "bXXXX"},
  "sha256": "..."
}
```

`registry.json` is a signed index of available models (id, version, url, sha256, size, languages). The extension downloads from it on demand.

## 5. Runtime plane

### 5.1 Components
```
vscode-extension/   (TypeScript)
  src/
    extension.ts            activation, commands, status bar
    router/
      detector.ts           language detection (see 5.2)
      policy.ts             model selection + fallback rules
      lifecycle.ts          LRU load/unload, memory budget, idle timeout
    host/
      llamaServer.ts        spawn/manage llama.cpp `llama-server` per model (random port, health checks)
      client.ts             OpenAI-compatible HTTP client (completions + chat, streaming, cancellation)
    providers/
      inlineCompletion.ts   vscode.InlineCompletionItemProvider, FIM prompt builder
      chat.ts               chat participant / webview panel
      codeActions.ts        explain / refactor / write tests commands
    registry/
      download.ts           fetch, verify sha256, install to globalStorage
    context/
      builder.ts            prefix/suffix windowing, imports, nearby open files, repo symbols
    telemetry.ts            LOCAL-ONLY metrics (latency, accept rate); opt-in export
  package.json              contributes: settings, commands, status bar
runtime-bin/                pinned llama.cpp builds per platform (win/mac-arm/mac-x64/linux)
```

### 5.2 Routing logic (policy.ts)
Priority order:
1. `document.languageId` → direct match in installed manifests.
2. Extension/glob match (`.tsx` → TypeScript model).
3. **Mixed-file handling:** embedded regions (SQL in Python strings, JS in HTML, Markdown code fences) → detect region by cursor position using tree-sitter / TextMate scopes and route to that region's language model if installed.
4. **Project sniff** for ambiguous cases (`.h` → C vs C++ via build files; `.js` in a TS project).
5. **Fallback chain:** nearest sibling model (JS↔TS, C↔C++, Java↔Kotlin) → user-configured generalist (optional) → "no model" with a one-click install prompt.
6. **Explicit override:** status bar picker pins a model for the file/workspace.

### 5.3 Lifecycle and resource policy
- Memory budget setting (default: 60% of free RAM). LRU eviction, idle unload after N minutes.
- Max concurrently loaded models default 2 (current-language + one recent).
- Prewarm the model for the active editor on window focus; load time target < 2 s with mmap.
- Single in-flight completion per editor; cancel on keystroke; debounce 150–250 ms.
- Latency budgets (CPU, M-series / modern x86): first-token < 300 ms for FIM with 1–2k-token context; ≥ 25 tok/s.

### 5.4 Context building (big quality lever for small models)
Small models gain a lot from good context. `builder.ts` assembles: file prefix/suffix windowing, import/dependency signatures, recently edited files, top-k relevant snippets via lightweight BM25 over the workspace (no embeddings needed initially), and LSP-provided type/definition info where available. Keep total prompt under context_length with a budget per segment.

### 5.5 Alternatives to consider
- **Runtime:** llama.cpp (baseline) vs ONNX Runtime / WebGPU (browser-hosted) vs MLX (Apple-only fast path). Keep the `host/` layer behind an interface so backends are swappable.
- **Router intelligence:** start rule-based (above). Later optional: a tiny classifier for ambiguous multi-language files. Do not use an LLM as the router at the start.

## 6. Evaluation (the quality gate)

Every model build must produce `eval_report.json` and pass thresholds relative to its base model and a stated competitor baseline.

| Category | Benchmarks | Gate |
|---|---|---|
| Function synthesis | HumanEval/MBPP, **MultiPL-E** (per-language) | ≥ base + X pts pass@1 |
| FIM / infilling | HumanEval-Infilling, SAFIM-style, own repo-derived FIM set | exact-match + edit-sim thresholds |
| Repo-level | RepoBench / CrossCodeEval for the language | no regression |
| Edit / refactor | CanItEdit-style, own held-out tasks | thresholds |
| Real-world | Held-out recent GitHub commits (post data cutoff), in-language | primary signal |
| Safety/quality | Compile rate, lint-clean rate, secret/license leakage probes | hard gates |
| System | Size, load time, tok/s, peak RAM on reference machines | **size < 1 GB hard gate** |

Decontaminate training data against all of these before reporting. Track per-language dashboards. A CI job re-runs the suite on every candidate checkpoint.

## 8. Milestones for Codex (each with acceptance criteria)

**M0: Skeleton & contracts**
- Create repo layout, `manifest.json` / `registry.json` JSON Schemas, TypeScript + Python types generated from schema.
- AC: schema validation tests pass; `make check` runs lint + tests in both Python and TS.

**M1: Vertical slice with an off-the-shelf model (no training)**
- Extension spawns llama.cpp with a downloaded GGUF, provides FIM inline completion for one language.
- AC: completions appear in VS Code on Python files; cancel/debounce works; integration test via `@vscode/test-electron` with a mock llama server.

**M2: Router + lifecycle**
- Implement detector/policy/lifecycle with two stub models (e.g., Python + TypeScript GGUFs), LRU eviction, status bar picker, fallback chain, mixed-file region routing.
- AC: unit tests for 30+ routing cases (including ambiguous `.h`, `.js` in TS repo, Markdown fences); memory budget respected under test.

**M3: Registry & installer**
- Download, sha256 verify, install to globalStorage, version upgrade/rollback, signed registry verification.
- AC: tamper test fails closed; offline mode works with installed models.

**M4: Verifier harness + eval suite (Python first)**
- Sandboxed test runner, MultiPL-E/HumanEval wiring, FIM eval builder from held-out repos, `gates.yaml`.
- AC: baseline model scored reproducibly (±1pt across 3 runs); report JSON emitted.

**M5: Data pipeline (Python first)**
- License filter, MinHash dedupe, tree-sitter parse filter, decontamination, FIM formatting, sharded tokenized output.
- AC: pipeline runs on a 1% sample end to end; contamination check reports zero overlap with eval sets; stats report per stage.

**M6: Training stages (Python first)**
- Config-driven CPT → SFT → rejection-sampling FT → QAT/quantize → package. Add vocab-pruning experiment.
- AC: `make train LANG=python` on a tiny smoke config runs end to end on 1 GPU in < 1 hr and yields a valid `.tcm` under size limit; full config documented.

**M7: Context builder & chat/edit features**
- BM25 repo context, LSP hints, chat panel, explain/refactor/test-gen commands with edit diff preview.
- AC: A/B harness shows context builder improves FIM eval on repo-level set.

**M8: Language fan-out**
- Add TypeScript, Rust, Go, Java, C/C++ by copying `configs/python.yaml` and implementing `verifiers/<lang>`.
- AC: each language reaches its eval gate; CI matrix builds all packages.

**M9: Hardening**
- Perf profiling on reference machines, crash recovery for server processes, telemetry (local), docs, marketplace packaging.
- AC: p95 first-token latency and memory budgets met on reference matrix.

## 10. Key risks and decisions to make early

1. **Base model choice and license**: confirm current permissive options before M6; this drives everything.
2. **Teacher-output licensing** for distilled SFT data: verify the teacher's terms allow training.
3. **1 GB ceiling vs quality**: 1.5B at Q4 is borderline; start at ~1B to leave room for the tokenizer, metadata, and vocab pruning.
4. **Does per-language specialization beat one multilingual 1B?** Run this ablation on Python early (M6): specialized vs multilingual at equal size. If the gap is small, a shared base plus small per-language LoRA deltas (~20-50 MB each) is a much cheaper design that fits the same router (router swaps adapters instead of models).
5. **Eval contamination** is the most common way tiny-model projects fool themselves; keep the held-out recent-commit set as the source of truth.
6. **Windows/macOS/Linux binary matrix** for llama.cpp adds packaging work; budget for it in M3/M9.
