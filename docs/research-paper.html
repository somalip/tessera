Abstract

Tessera is a VS Code extension that uses local editor context to select compact language models and shape inference requests. It distinguishes short fill-in-the-middle completions, comment-driven generation, and chat, and manages the llama.cpp processes that serve those models. Its design lets users configure a small model for routine editing while reserving a separate checkpoint for larger Python requests. A repository smoke test recorded nine AST matches in twelve fast-completion prompts. In a separate eight-program evaluation, the configured Python model passed one task and a 7B reference passed three under different serving configurations. Dual-process theory offers a framework for asking when a quick default is useful and when a task warrants explicit constraints and checks. Tessera approximates this division through request routing. The recorded results characterize two workloads and leave the benefit of routing itself open to controlled testing.

1. Problem and scope

Inline completion must respond during an edit and fit the surrounding code. A standalone program request must preserve requirements and produce enough text to implement them. Chat needs conversation history and may use a selection from the editor. Tessera treats these as separate request types and chooses models and prompt budgets accordingly. This paper examines the 0.1.8 VSIX, its runtime implementation, and the repository reports for Python autocomplete and standalone generation. [1–4]

2.1 System 1 and System 2 as modes of reasoning

Evans and Stanovich distinguish Type 1 processes, often called System 1, by their autonomy. An experienced programmer may expect return after reading a function signature and its body. Type 2 processing, often called System 2, relies on working memory to hold and manipulate hypothetical possibilities. A programmer might compare what a function should return for an empty input, a missing field, and a field whose value is zero. Each hypothetical case can be evaluated against the same contract. Speed is a common correlate. The defining distinction in this account is how the response is produced. [9]

A plausible default can begin a train of thought that later checks revise. In a default-interventionist account, Type 1 supplies a candidate response and Type 2 can intervene when a goal, rule, or detected conflict calls for further reasoning. The candidate may survive review, and deliberation can still go wrong if the reasoner overlooks a constraint. For coding, this suggests distinguishing local plausibility from evidence that a proposed implementation satisfies the specification. [9]

2.2 The low road and high road in auditory conditioning

Romanski and LeDoux used lesions to investigate how direct and indirect auditory pathways contribute to conditioned responses to a simple sound. Their results support multiple routes to the amygdala in that setting. Pessoa and Adolphs later questioned whether a privileged subcortical route adequately explains primate visual emotion processing and emphasized the interplay of multiple pathways. The road terminology describes sensory circuitry in one literature, while System 1 and System 2 describe functional properties of reasoning in another. Tessera borrows the idea of routing a task through different amounts of processing as an engineering analogy. [10] [11]

3. Request routing in Tessera

Tessera chooses a path from observable editor signals, including request type, cursor position, and model configuration. When a route calls for language detection, file and workspace pins can affect selection, and cursor context can distinguish a Markdown code fence or SQL embedded in Python. Selected models run on local llama.cpp processes. [1, 2, 5]

  1. Fast autocomplete. The provider formats a bounded prefix and suffix around the cursor using the model’s fill-in-the-middle tokens. The fast Python profile uses a 768-token context, caps output at 32 tokens, and stops at the first newline. It skips repository retrieval on this route. [2, 3]
  2. Short Python comments. A configured structured-data model can turn the comment into a brief. The extension accepts a shorter single line only when checks preserve quoted literals and recognized interface markers and retain a negation marker when the source has one. Otherwise it falls back to the cleaned request. The Python generation model uses the resulting text with code context. These checks cover specific features of the request. Semantic equivalence remains unmeasured. [2]
  3. Standalone Python programs. A recognized top-level program comment takes a direct path to the Python generator. The provider preserves adjacent requirements and can retry once for incomplete output or invalid Python syntax. Syntax validity checks whether Python can parse the response. Functional correctness requires separate tests. [2, 4]
  4. Chat and editor actions. The chat path uses a chat-capable local model. Explain, refactor, and test-generation actions use editor context. Refactors and generated tests are presented in a diff for review. [2]

3.1 What the analogy predicts

Suppose an editor request asks for a function that retrieves a setting while preserving an explicit value of 0. A completion such as value or default is locally idiomatic and syntactically valid, yet it replaces zero with the default. Holding the requirement in the prompt gives the generator access to the relevant constraint. An assertion for the zero case can then distinguish the two behaviors. The production retry checks a narrower class of problems. The standalone evaluation supplies behavioral assertions in a separate harness. [2, 4]

This distinction yields two engineering predictions. Bounded context should help routine edits when nearby code carries enough information to infer the user's intent. A route that preserves more requirements should help tasks whose behavior depends on constraints outside the immediate cursor neighborhood. Both predictions concern observable behavior, including acceptance, latency, and correctness. The reported experiments offer preliminary evidence about specific configurations, while a matched routing experiment is needed to test these predictions directly.

4. Weights and runtime

Users can assign raw GGUF weights to model roles. The extension can also consume signed registry entries and versioned model packages when configured with a registry URL and trusted key. A package manifest hashes the GGUF, and the registry entry hashes the whole package. Each model package must be smaller than one billion bytes. The downloadable fast Python checkpoint applies a merged LoRA update to Qwen2.5-Coder-0.5B before IQ4_NL quantization. The structured-data checkpoint uses the stock 0.5B base in Q4_K_M. The experimental documentation, English, diagram, and summary variants share Qwen3.5-0.8B tensors and specialize the chat template with system instructions. Their specialization applies when the runtime renders that template. [1–3, 7, 8]

The extension starts llama.cpp servers on loopback and manages resident models under an estimated memory budget. Inference leases protect active models during eviction, and a replacement waits for the evicted process to exit. Under the automatic budget, an oversized model can run alone with unlocked memory-mapped weights on CPU. The operating system can reclaim mapped pages, so disk activity may rise under memory pressure. GGUF file size measures storage. Working memory also depends on context, runtime buffers and, when enabled, GPU offload. Keeping more than one model resident can add memory demand, while loading or switching models can increase time to the first suggestion. [1, 2, 5]

5. Comparison with a single large local model

Consider a setup in which an editor client sends every request to a single 7B model through a local Ollama server. The client selects a model and passes chat messages to Ollama’s local API. Ollama also exposes a keep-alive control for model residency. Tessera couples its model and prompt choices to events in VS Code and manages its own llama.cpp processes. Integration code can reproduce the same routing policy with other runtimes. Local inference is shared by both configurations. [1, 2, 5, 6]

6. Evaluation methods and results

6.1 Workloads and scoring

The unit of analysis was one prompt or programming task. The autocomplete suite compared the generated Python syntax tree with the expected tree. The standalone suite scored whether a generated program passed its task-specific assertions. Each comparison uses the workload and runtime settings recorded in its source report. [3, 4]

6.2 Fine-tuned checkpoints

The fast autocomplete model merged a rank-8 LoRA update into Qwen2.5-Coder-0.5B before IQ4_NL quantization. Training used 96 original CC0-1.0 examples for comment and partial-line completion. The resulting GGUF was 354,304,640 bytes. [3]

The standalone Python candidate trained for two LoRA epochs with 589,824 trainable parameters in the last four Qwen2.5-Coder blocks. Its 48 examples comprised 5 examples generated by the pinned 7B model, 11 original program solutions, and 32 replay examples. The Q4_0 export was 934,954,496 bytes and the Q4_K_M export was 986,048,000 bytes. [4]

6.3 Recorded results

The autocomplete report measured twelve held-out prompts on CPU using llama.cpp b12244. It recorded 9/12 AST matches for the 354 MB fast checkpoint and 7/12 for a stock 398 MB Q4_K_M checkpoint. Their median first-token latencies were 75 ms and 167 ms respectively. These timings exclude VS Code debounce, router waits, and rendering. AST matching can miss equivalent solutions, and the comparison varies quantization as well as tuning. [3]

The standalone-program report used eight requests and job-specific assertions in a pinned, network-disabled Python container. The configured 934,954,496-byte Python checkpoint passed 1/8 on CPU. The 4,683,073,536-byte 7B reference passed 3/8. The reference had a 2,048-token slot and a 1,250-token output cap, while the compact checkpoint ran through the inline provider with a 4,096-token context and its own output budget. The scores reflect the full configurations, including prompts and inference settings. This experiment cannot isolate model size as the cause of the difference or establish an Ollama performance baseline. [4]

Adding an implementation checklist to the Q4_0 candidate passed 2/8 programs on Metal and 1/8 on CPU. A quarter-strength LoRA update with the checklist passed 0/8 on Metal. The released configuration kept the checkpoint that passed more short chat tests. [4]

6.4 Chat-template specialty smoke checks

These four Qwen3.5-0.8B variants share the same weights and apply specialty instructions through their chat templates. Each variant had its own small suite, including one check for English editing. [8]

7. Limitations and follow-up study

The recorded suites cover a small set of Python tasks. The autocomplete study changes quantization alongside tuning, and the standalone study varies serving and prompt settings. Neither experiment estimates the independent effect of route selection. A useful follow-up would pair each task across conditions and stratify the tasks by where their requirements appear. Local tasks could derive their answer from the prefix and suffix. Constraint-heavy tasks could include a nearby instruction about a boundary case or an interface contract.

  1. Isolate routing. Use the same checkpoint, quantization, serving stack, hardware, and sampling settings for both conditions. Compare the routed prompt and output budget with a fixed policy on the same tasks. Record the chosen route and report results by task stratum.
  2. Isolate intervention. On the standalone route, compare the first candidate with the final output after the existing retry policy. Record retry frequency, parse recovery, and task assertion pass rates. This tests whether the extra step improves behavior as well as syntax.
  3. Measure the editor cost. Report cold and warm time to first visible suggestion, peak memory, and acceptance or corrective edits. Record process starts and model switches so that host overhead can be distinguished from generation time.

Use licensed fixtures with documented decontamination from training and keep behavioral checks in the evaluation harness. Report counts alongside rates and uncertainty on paired differences. If the extra processing adds latency and the constraint-heavy tasks show no improvement in assertions, the expected benefit of routing would lack support for that configuration. [1, 3, 4]

8. Conclusion

Dual-process theory sharpens the engineering question Tessera raises. A brief completion can be valuable when context is local and the user can inspect it immediately. A standalone program needs a prompt that preserves requirements and an evaluation that checks behavior. Tessera implements distinct request paths within a local runtime, and its recorded studies establish workload-specific baselines for testing when that distinction improves the editing workflow.
